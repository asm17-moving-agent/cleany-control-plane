# ADR 0008 — 날짜 중심 작업 관리와 결과 검토 기록

- 상태: 구현
- 날짜: 2026-11-17

## 문제

작업 요청과 결과가 별도 화면에 있어 진행 상태를 따라가기 어렵다. 기존 공통 snapshot은
최신50건이므로 이 목록만 날짜로 필터링하면 과거 작업과 일별 건수를 누락한다.
또한 화면 열람만으로 결과를 확인한 것으로 처리하거나 terminal payload에 검토 상태를
저장하면 기존 결과 불변성 계약을 훼손한다.

## 결정

`/missions`에 날짜 선택·일별 요약·목록·상세·요청을 통합한다. `/results`는 쿼리를
보존해 이 화면으로 이동한다. 기존 생성·취소·실행 상태·관측 API를 재사용한다.
재시도는 기존 결과를 보존하고 새 idempotency key로 새 요청을 등록한다.

`GET /api/missions?day=YYYY-MM-DD`는 Asia/Seoul 요청일 또는 종료일이 같은 작업을
반환한다. 오늘에는 이전 날짜에 요청한 미종료 작업도 포함한다. 같은 작업이 요청일과
종료일 양쪽에 나타날 수 있으므로 이 수치는 일별 매출/생산량 통계가 아니다.
날짜 생략 시 기존 최신50건 계약을 유지하며 UI는100건씩 기존 커서를 끝까지 조회한다.
`GET /api/missions/{id}`는 최신 snapshot 밖의 직접 링크를 지원한다.

`POST /api/missions/{id}/review`는 명시적 검토 완료이다. 첫 확인자와 시각을 별도
SQLite `mission_reviews` 테이블에 저장한다. 기존 terminal JSON·sequence·outcome·
로봇 보고 `needs_human_review`는 바꾸지 않는다. 응답에 optional `review`를 합성하며
새 기록만 `mission.reviewed` 알림을 발행한다. 재전송은 같은 응답을 반환한다.
조회·검토는 고객/선택 시설 범위를 검사하고 검토에는 기존 Origin/CSRF/세션 검사를 적용한다.
종료 전 검토는409이다. 이 작업은 실행 승인이나 Robot FSM 상태 변경이 아니다.

## 비용과 검증

일별 전체 조회는 최신 snapshot보다 요청량이 크다. 현재 단일 로봇 범위에서는100건씩
페이지를 읽되, 대규모 이력이 되면 서버 집계 및 가상 목록 도입을 별도로 검토한다.
시설별 시간대 설정이 없는 현재 제품에서는 한국 날짜를 사용한다.

기존 DB에는 별도 테이블만 추가한다. 종료 payload를 수정하는 migration은 없다.
테스트는 날짜 경계·자정 넘김·대기 이월·100건 초과·고객/시설 격리·CSRF·검토 중복·
재시작 후 유지·원본 terminal payload 동일성·깊은 링크·재시도 새 요청을 검증한다.
디자인 기준과 비교 방법은 [UI 명세](../architecture/dashboard-design-system.md)를 따른다.

## 후속: 캘린더 표시와 작은 일별 요약

상단 통계 바를 없애고 캘린더 아래 전체/완료/확인 필요 카드로 이동했다. 날짜별 초록 점과
주황 점은 기존 일별 API 및 검토 판정으로 계산한다. 날짜 선택/월 탐색과 목록/상세 구성은 유지한다.
API나 모델을 추가하지 않고 달력에 보이는 날짜만4개씩 병렬 조회하여100건 cursor를 끝까지
읽는다. 고객/시설/범위 캐시, 월 전환 취소, 갱신/검토/SSE 무효화, 기존 설정 기반 연결 끊김
시 재조회가 적용된다. 최신50건만 사용하거나 요청일만 보고 월 이력을 조기 종료하면 월 경계를
넘긴 종료 기록을 놓치므로 그러한 추정은 하지 않는다. API 호출량은 날짜 수에 비례하며,
향후 대규모 이력에서의 서버 집계는 별도 계약 변경으로 다룬다.
